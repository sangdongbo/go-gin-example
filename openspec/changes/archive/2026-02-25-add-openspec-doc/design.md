## Context

项目已经成功使用 OpenSpec 工作流管理了多个变更（如 add-readme1-file 和 add-readme2-file），这些变更都遵循了 spec-driven 模式的完整生命周期。然而，项目缺少一份系统性的文档来说明 OpenSpec 的使用方法。

当前状态：
- 项目已初始化 OpenSpec（存在 openspec/config.yaml）
- 已有两个归档的成功案例可作为参考
- 团队已熟悉 propose → apply → archive 的基本流程
- 使用 spec-driven 工作流模式

目标用户：
- 新加入项目的开发者
- 需要了解变更管理流程的团队成员
- 希望参考 OpenSpec 最佳实践的使用者

## Goals / Non-Goals

**Goals:**
- 创建一份完整的 OpenSpec 中文使用指南
- 详细说明四个核心命令：propose、apply、archive、sync
- 解释 spec-driven 工作流的各个工件（proposal、design、specs、tasks）
- 提供实际操作示例和完整的工作流演示
- 说明常见场景和最佳实践
- 使内容易于理解，适合中文用户阅读

**Non-Goals:**
- 不替代 OpenSpec 官方文档（如果存在）
- 不涉及 OpenSpec CLI 的安装和配置
- 不讨论其他工作流模式（仅关注 spec-driven）
- 不包含项目特定的业务逻辑说明

## Decisions

### 决策 1: 文档位置和命名
**决定**: 将文档命名为 `openspec.md` 并放置在项目根目录

**理由**:
- 与 README.md、README1.md、README2.md 等文档保持一致的命名风格
- 根目录位置便于快速访问和发现
- 文件名直观地表明了文档主题

**替代方案**:
- 放在 `docs/` 目录下：但会降低可见性，不适合作为重要的工作流文档
- 命名为 `OPENSPEC_GUIDE.md`：过于正式，不符合项目现有文档的命名风格

### 决策 2: 文档结构和章节组织
**决定**: 采用渐进式结构，从概览到详细命令，再到实践场景

**结构**:
1. OpenSpec 简介
2. 核心概念（工作流、工件类型）
3. 完整工作流程图
4. 命令详解（propose、apply、archive、sync）
5. 工件详解（proposal、design、specs、tasks）
6. 实践场景和示例
7. 最佳实践和注意事项
8. 常见问题解答

**理由**:
- 先整体后局部，符合认知规律
- 既适合新手从头阅读，也适合熟练用户快速查找
- 实际示例帮助理解抽象概念

**替代方案**:
- 命令参考手册式：过于枯燥，不适合学习
- 纯教程式：缺乏结构化参考价值

### 决策 3: 内容深度和示例选择
**决定**: 提供详细的命令说明，并使用项目实际案例作为示例

**具体做法**:
- 每个命令包含：用途、语法、参数说明、输出示例
- 使用 add-readme1-file 和 add-readme2-file 作为完整工作流示例
- 提供实际的目录结构和文件内容片段
- 包含成功和失败场景的处理建议

**理由**:
- 实际案例比虚构示例更有说服力和参考价值
- 详细的命令说明减少查询外部文档的需要
- 真实的项目结构帮助用户快速定位文件

**替代方案**:
- 使用通用示例：缺乏项目特定的上下文
- 仅提供简短说明：不足以支撑独立使用

### 决策 4: 语言和术语处理
**决定**: 全程使用中文，技术术语提供英文原文

**具体做法**:
- 主要内容完全使用简体中文
- OpenSpec 特定术语（如 proposal、design、specs、tasks）首次出现时标注英文
- 命令和代码块保持原始英文形式
- 文件路径和配置示例使用实际英文路径

**理由**:
- 与用户需求一致（"全程使用中文"）
- 保持技术准确性（命令和路径不能翻译）
- 首次标注英文帮助用户关联原始文档

### 决策 5: 与现有文档的关系
**决定**: 作为独立的工作流文档，与 README 系列互补

**定位**:
- README.md: 项目整体介绍（English）
- README1.md: 双语学习指南
- README2.md: 深度中文学习指南
- openspec.md: OpenSpec 工作流使用规范

**理由**:
- 各文档职责清晰，互不重叠
- openspec.md 专注于变更管理流程，不涉及项目业务
- 便于维护和更新

## Risks / Trade-offs

### 风险 1: 文档与 OpenSpec CLI 版本不同步
**描述**: OpenSpec CLI 可能更新命令或改变行为，导致文档过时

**缓解措施**:
- 在文档开头注明编写时的 OpenSpec CLI 版本
- 定期检查并更新文档
- 使用实际命令输出作为示例，便于验证

### 风险 2: 示例过于项目特定
**描述**: 使用项目实际案例可能导致示例不够通用

**接受理由**:
- 实际案例的教学价值超过通用性的损失
- 用户可以通过类比理解如何应用到自己的场景
- 文档主要服务于本项目团队

### 权衡 1: 详细程度 vs 简洁性
**选择**: 倾向于详细，提供完整的上下文和示例

**理由**:
- 工作流文档需要准确性，宁可详细也不要遗漏关键信息
- 用户可以跳过熟悉的部分
- 对新手更友好

### 权衡 2: 中文纯度 vs 技术准确性
**选择**: 优先保证技术准确性，命令和路径保持英文

**理由**:
- 翻译技术术语可能导致混淆
- 用户在实际使用时需要输入准确的英文命令
- 中文解释已经足够清晰

## Migration Plan

不适用 - 这是新增文档，无需迁移。
