## Context

当前项目 note 目录下有两个 Go 知识总结文档：
- **note1.md**: 覆盖基础容器（slice/map/string）和 GMP 调度模型
- **note2.md**: 覆盖性能优化实战案例（CPU/GC/锁/goroutine）

现有文档风格已经成熟，采用"面试题 → 标准答案 → 追问 → 实战案例"的结构。为了构建完整的 Go 面试知识体系，需要补充其他高频考点。

## Goals / Non-Goals

**Goals:**
- 创建 6 个新的知识总结文档，覆盖 Go 面试剩余核心主题
- 每个文档保持与 note1.md、note2.md 相同的风格和深度
- 内容包含面试题、标准答案、追问点、代码示例
- 形成系统化的 Go 面试知识库，方便快速查阅和复习

**Non-Goals:**
- 不涉及项目源代码修改
- 不创建新的代码示例项目
- 不编写 Go 语言入门教程（假定读者已有基础）
- 不覆盖第三方框架（如 gin、gorm）的面试题

## Decisions

### 决策 1：按主题拆分为 6 个独立文档

**理由**：
- 每个文档聚焦单一主题，便于查阅和记忆
- 与现有 note1.md（基础容器）、note2.md（性能调优）形成主题互补
- 单个文档长度控制在 300-400 行，适合面试前快速复习

**替代方案**：创建一个大的 note3.md 包含所有内容
- **不选理由**：文档过长不利于查找，主题混杂降低复习效率

### 决策 2：6 个主题优先级

选择的 6 个主题基于面试高频度排序：
1. **channel 和并发模式** - Go 最核心特性，必考
2. **interface 和反射** - 类型系统基础，高频
3. **defer/panic/recover** - 错误处理机制，常考
4. **context 使用** - 并发控制标准库，实战必备
5. **内存管理和 GC** - 性能优化基础，深度题常考
6. **测试和 benchmark** - 工程实践，大厂必问

**不包括的主题及理由**：
- Go modules：偏工具使用，面试较少深入考察
- cgo：使用场景有限，非通用考点
- 汇编优化：超出一般面试范围

### 决策 3：内容结构复用现有模式

采用 note1.md 和 note2.md 已验证的结构：
```markdown
# 主题名称
## 小节 1️⃣
### 面试题
### 标准答案
### 追问 1/2/3
### 代码示例（如需要）
```

**理由**：
- 风格统一，减少认知负担
- 结构清晰，便于快速定位答案
- 已被实践验证有效

### 决策 4：中文编写，关键术语标注英文

与现有文档保持一致：
- 主要内容用中文表达
- 关键术语标注英文原文（如 `goroutine`、`channel`、`GC`）
- 面试题用中文提问，便于记忆

**理由**：面试场景多为中文环境，但需要准确使用英文术语展现专业性

### 决策 5：每个主题包含 5-8 个核心考点

**理由**：
- 覆盖该主题的主要面试问题
- 深度适中，既不过于简单也不过度深入冷门细节
- 单个考点控制在半页到一页，便于面试前快速浏览

## Risks / Trade-offs

### 风险 1：内容可能与现有文档有部分重叠

**示例**：内存管理主题可能与 note2.md 的 GC 案例有交叉

**缓解**：
- 新文档侧重原理和概念（如三色标记算法）
- note2.md 侧重实战案例和 pprof 分析
- 交叉部分通过交叉引用关联

### 风险 2：Go 版本差异导致内容过时

**示例**：GC 算法、调度器在 Go 版本间有演进

**缓解**：
- 文档开头标注适用 Go 版本（1.18+）
- 提及重要版本差异（如"Go 1.14 前的 GC STW 更长"）

### 权衡 1：深度 vs 广度

**选择**：优先保证每个主题的核心考点覆盖，而非单个考点的极致深度

**理由**：
- 面试时间有限，面试官更倾向考察知识面广度
- 极深的细节（如汇编级别的实现）在实际面试中较少涉及
- 如后续需要加深，可以独立扩展某个主题文档

### 权衡 2：代码示例完整性 vs 可读性

**选择**：代码示例尽量精简，只保留核心逻辑

**理由**：
- 面试复习场景需要快速理解，不是生产代码
- 可通过注释和说明补充完整性
- 复杂示例可以分步骤展示
