# 一、基础容器内功（slice / map / string）

## 1️⃣ Slice 扩容机制（高频）

### 面试题

**切片和数组的区别？切片扩容时发生了什么？**

### 标准答案

* **数组**：值类型，长度固定，拷贝成本高
* **切片**：三元组结构（`ptr + len + cap`），指向底层数组

### 扩容机制（Go 1.18+ 概括）

> 本质：**申请新数组 → 拷贝旧数据 → 返回新 slice**

经验规则（不是精确值）：

* 原 cap < 1024：**近似翻倍**
* 原 cap ≥ 1024：**按较小增幅增长（~1.25x），趋向平滑**

⚠️ 扩容并非严格 2x / 1.25x，runtime 会综合：

* 申请大小
* 内存对齐
* 分配器策略

### 追问 1：扩容一定发生拷贝吗？

* **是**
* 除非你 append 的正好是同一个 slice 的子切片（极少）

### 追问 2：为什么 append 后原 slice 数据“没变”？

* 因为已经指向 **新底层数组**
* 原 slice 仍指向旧数组

---

## 2️⃣ Map 是否线程安全（必考）

### 面试题

**多个 goroutine 并发读写 map 会怎样？**

### 标准答案

* **不安全**
* Go 在运行时检测到并发写，会直接 `fatal error`
* 原因：map 扩容、rehash 过程中结构会变化

### 追问 1：为什么并发读 + 写也会 panic？

* 因为 **读操作可能读到不一致的 bucket 状态**
* runtime 不做读写并发保护

### 追问 2：sync.Map 适合什么场景？

* 读多写少
* key 生命周期长
* goroutine 之间共享缓存、配置

⚠️ **高频写入场景，sync.Map 性能反而更差**

---

## 3️⃣ string 与 []byte

### 面试题

**string 转 []byte 会不会拷贝？**

* 正常转换：✅ 拷贝
* unsafe 转换：❌ 不拷贝（但破坏只读语义）

### 追问

**为什么 string 设计成不可变？**

* 可作为 map key
* 可共享底层数据
* 简化 GC 与并发模型

# 二、调度内功：GMP 模型（核心）

## 4️⃣ GMP 调度模型

### 面试题

**简述 GMP 各自职责**

* **G**：goroutine，执行单元
* **M**：OS 线程
* **P**：调度上下文，决定并发度（`GOMAXPROCS`）

规则：

* **M 必须拿到 P 才能跑 G**
* **P 持有本地 runnable 队列**

---

### 追问 1：为什么一定要有 P？

> 为了解耦 **内核线程数量** 与 **并发任务数量**

* 没有 P → 每个 G 绑定一个 M → 退化成线程模型
* 有 P → 控制并发上限，减少线程切换

---

### 追问 2：Work Stealing 怎么偷？

* P 本地队列空了
* 从 **其他 P 队列尾部** 偷取一半 G
* 减少锁竞争 + 提高负载均衡

---

### 追问 3：M 阻塞在 syscall 时发生了什么？

* M **释放 P**
* runtime 新建 / 唤醒 M 接管该 P
* 阻塞 syscall 的 M 返回后，重新抢 P

👉 **这就是 Go 能抗高并发 IO 的关键**

---

# 三、Channel 内功（不是“会用就行”）

## 5️⃣ Channel 底层

### 面试题

**channel 是锁还是无锁？**

* **有锁**
* 结构：mutex + buffer + sendq + recvq
* select 是 runtime 级调度，不是语言级原子

---

### 已关闭 channel 行为（必背）

| 操作            | 结果           |
| ------------- | ------------ |
| send          | panic        |
| close 再 close | panic        |
| receive       | 返回零值 + false |

### 追问

**为什么 receive 不 panic？**

* 关闭 channel 是广播语义
* 允许消费者正常退出
* 关闭的 channel 不会 panic 是为了让接收方能安全地消费掉缓冲区里的余量，并能通过零值感应到“数据流已结束”。

---

### 工程原则

> **谁发送，谁关闭**

* 接收方不关
* 多发送者 → 用 once / 上层协调

# 四、接口（interface）内功（高级分水岭）

## 6️⃣ iface / eface
* eface 代表空接口 interface{}（或者 Go 1.18+ 中的 any）因为空接口不包含任何方法，所以它只需要维护类型信息和数据指针。
* iface 代表非空接口（即定义了方法的接口，如 io.Reader）。它比 eface 复杂，因为它需要存储方法表，以便在运行时进行动态派发。

## 📋 Go 接口底层实现对比：eface vs iface

| 特性 | **eface** (空接口) | **iface** (非空接口) |
| --- | --- | --- |
| **对应类型** | `interface{}` / `any` | 带方法的接口（如 `error`, `io.Reader`） |
| **内部关键组件** | `_type` (动态类型信息) | `itab` (包含方法表、具体类型信息) |
| **方法调用** | 不支持直接调用方法 | 支持通过 `itab.fun` 快速调用（动态派发） |
| **主要用途** | 容器、反射、接收任意类型数据 | 实现抽象、多态、逻辑解耦 |

### 🔍 深度解析

### 1. eface (Empty Interface)

`eface` 结构非常简单，仅用于记录数据的位置及其所属类型。

* **`_type`**: 指向类型的元数据，描述了值的大小、对齐方式、哈希等。
* **`data`**: 指向具体数值的指针。

### 2. iface (Interface)

`iface` 更加复杂，因为它是多态的核心。

* **`itab`**:
* `inter`: 接口本身的元数据。
* `_type`: 具体实现类的元数据。
* **`fun`**: 核心函数表。在赋值时，Go 会预先找到接口方法在具体类型中的地址并存在这里。当你调用接口方法时，Go 无需查找，直接跳转到 `fun` 存储的地址执行。
---

### 面试题

**为什么 `nil` 接口不等于 `nil`？**

* interface = **(type, data)**
* 只有两者都为 nil，接口才为 nil

```go
var p *int = nil
var i interface{} = p // type ≠ nil
```

---

### 追问 1：interface 为什么慢？

* 装箱（boxing）
    * 将值类型包装在引用类型（eface/iface）中，并将其迁移至堆上。
    * 分配内存（通常在堆上）：由于接口持有的 data 是一个指针，Go 运行时通常需要在堆上申请一块内存来存放值 100。
    * 值拷贝：将原始数据拷贝到新申请的内存空间中。注意：接口不持有原始变量的引用，而是持有副本。
    * 构建 eface/iface 结构体：填充 _type 指针，指向 int 的类型元数据。填充 data 指针，指向步骤 1 中分配的堆内存地址。
* 逃逸到堆
* 动态派发，难以内联

### 追问 2：什么时候必须避免 interface？

* 高频循环
* 性能敏感路径
* 数值计算

# 七、终极自检（你能答，内功就稳）

## 1. Goroutine 阻塞 IO 时 Runtime 做了什么？

当 Goroutine 执行网络 IO 等待时，它并不会让操作系统线程（M）进入阻塞状态，而是通过 **网络轮询器（NetPoller）** 进行异步处理。

* **挂起 G**：当前的 Goroutine 会被设置为 `_Gwaiting` 状态，并从处理器（P）的运行队列中解绑。
* **注册事件**：Runtime 将该 G 对应的文件描述符（fd）注册到 NetPoller（底层使用 `epoll/kqueue/iocp`）。
* **释放 M**：与之绑定的线程 M 释放，转而去执行 P 队列中的其他 Goroutine，保持 CPU 高效利用。
* **唤醒**：当 IO 事件就绪，NetPoller 会收到内核通知，将该 G 重新放入 P 的全局/本地队列，等待调度执行。

---

## 2. Slice 扩容为什么会导致数据错乱？

Slice 本质上是一个结构体（包含指向底层数组的指针、长度 `len`、容量 `cap`）。“数据错乱”通常发生在**并发读写**或**共享底层数组**的场景下。

* **非原子性操作**：Slice 的扩容涉及申请新空间、拷贝旧数据、更新指针。这三个步骤并非原子的。
* **地址变更**：当扩容发生（例如 `append` 超过 `cap`），Slice 会分配新地址。如果此时有另一个变量仍持有指向旧地址的 Slice，两者对同一逻辑索引的修改将指向不同的内存物理地址，导致状态不一致。
* **并发竞态**：多个 Goroutine 对同一个 Slice 进行 `append`，可能会由于并发更新 `len` 和指针，导致部分数据被覆盖或丢失。

---

## 3. Interface 为什么导致逃逸？

Interface 导致逃逸的核心原因在于：**编译器在编译期无法确定具体类型及其所需内存大小**。

* **动态分发**：Interface 包含 `itab` 和 `data` 指针。编译器无法静态分析出接口变量最终会指向哪个具体的实现类。
* **生命周期不确定**：由于具体类型未知，编译器无法确定该变量在函数返回后是否仍被引用。
* **保守策略**：Go 编译器为了保证安全，会将这种“类型不确定”且“生命周期难以追踪”的变量从栈分配转移到堆上（Heap），由 GC 管理。

---

## 4. Map 为什么并发写直接 Fatal？

Go 官方设计 Map 时选择不支持并发写，并会在检测到并发写时直接抛出 `fatal error: concurrent map writes` 导致崩溃，而非通过加锁来保证。

* **性能优先**：Map 的应用场景极其广泛，强制加锁会严重拖累 90% 以上不需要并发写的单线程性能。
* **结构脆弱**：Map 扩容时会涉及哈希桶（Bucket）的迁移。如果并发写，可能导致哈希链表死循环、内存溢出或数据指针指向垃圾地址。
* **快速失败原则**：并发写 Map 通常意味着逻辑 bug。与其允许数据在错误的基础上继续运行产生不可预知的后果，不如直接崩溃，强迫开发者在代码层面通过 `sync.Mutex` 或 `sync.Map` 解决。

---

## 5. GC 为什么一定要 STW？

**STW (Stop The World)** 是为了确保在特定阶段内存引用关系的“绝对一致性”。

* **写屏障的局限性**：虽然 Go 使用了三色标记法和插入/删除写屏障来减少 STW 时间，但在 **开启/关闭屏障** 以及 **扫描栈空间** 的阶段，必须暂停世界。
* **防止漏标（假阴性）**：如果不 STW，当 GC 标记指针时，用户程序（Mutator）可能删除了一个指向黑色对象的指针，并将其重新指向一个白色对象。如果没有 STW 捕捉这种瞬间变化，该白色对象会被误认为不可达而回收，导致**悬挂指针**。
* **栈扫描一致性**：Goroutine 的栈是私有的且移动频繁，扫描栈时必须暂停该 G，以防止在扫描过程中栈指针发生变化。
